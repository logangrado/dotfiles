# Task: first-class-worktrees

**Status**: complete
**Branch**: hatchery/first-class-worktrees
**Created**: 2026-07-17 13:50

## Objective

I work with a lot of worktrees, via hatchery, as you can probably tell.

However, I encounter significant friction using worktrees day to day in emacs. I use doom emacs, which is well setup for a project-first mindeset, but doesn't work well for worktrees.

Current setup:
- Project-based with projetile/persp-mode
- I have one pane per project, split in to a few windows
  - I switch between projects with spc-tab <NUMBER>
- I open files with spc-spc (projectile-find-file)
  - it shows the current worktree in the search bar
- I open terminals in the current project using lg/vterm-here-workspace (and associated methods)  
- using magit, I can easily see what worktrees _exist_, and see worktrees in the log (any worktree shows up as a box around a branch)

However, this falls very flat in several ways:
- Worktree switching:
  - I can open magit and switch worktrees. However, this often doesn't quite work right.
    - sometimes, it's correct. the worktree changes, and spc-spc opens files in the correct worktree
    - sometimes, it doesn't seem to switch at all
- buffers:
  - buffers are _supposed_ to be grouped by worktree, but it doesn't seem to work very well.
- worktree status:
  - I have no way of knowing which worktree I am in at any given moment without switching to magit
- terminals:
  - opening terminals always opens in the repo root, not the current worktree. I have to use `hatchery shell` or manual `cd` to get to the right dir

Help me come up with a solution to this problem. what are good ways to address this? how can the worktrees become a first-class citizen?

## Summary

**Status**: complete (pending the user's live verification in Emacs — this sandbox has no Emacs binary, so all checks below are manual code review, not a running test).

Persps stay one-per-project as required; worktree identity lives per-buffer via the existing `lg/project-display-name` (`00-worktree.el`), not per-persp.

Key decisions:
- **Terminal bug root cause**: `lg/vterm-get-workspace-buffer-name`/`lg/vterm-next-workspace-buffer-name` (`vterm.el`) keyed terminal buffer identity only by persp name. Fixed by routing both through a new shared `lg/vterm--workspace-name` (`vterm-reindex-buffers.el`), which prefers `lg/project-display-name` (worktree-aware: `"<repo>"` main tree, `"<repo>:<worktree>"` inside a worktree) and falls back to persp name when no project is detected. All existing regex-based name parsing in that file already used `regexp-quote` on the workspace string, so it tolerates the new `:worktree` suffix with no changes.
- **Two distinct worktree operations**, since real usage showed they're not the same thing: "open a file in a worktree" (always prompts) vs. "switch to a worktree" (jump to whatever's already open there, like switching a persp). `doom.d/packages/persp-worktree.el`:
  - `lg/worktree--list` wraps `magit-list-worktrees` into an ordered `(label . path)` alist — this order is the canonical numbering used everywhere else (tab-bar segment, `switch-to-N` commands).
  - `lg/worktree-switch` (`SPC p w`) — original behavior, unchanged: `completing-read` + always `projectile-find-file`/`dired` at the chosen worktree.
  - `lg/worktree-switch-to-path` / `lg/worktree-quick-switch` (`SPC p j`) / `lg/worktree-switch-left`/`right` (`SPC p {`/`}`) / `lg/worktree-switch-to-1..9` (`SPC p 1..9`) — all route through `lg/worktree--buffer-for-path`, which finds the most-recently-used live buffer already rooted at that worktree (via `buffer-list`'s MRU ordering) and `switch-to-buffer`s it; only falls through to the file prompt if nothing's open yet there.
- **Visual indicator**: went through three iterations. First attempt rendered via `tab-line-format` directly — nothing appeared. Second attempt worked around that by folding the indicator into the existing `tab-bar-format` persp row instead. Root cause of the first failure was eventually found: **centaur-tabs auto-detects `tab-line-format`'s availability (Emacs 27+) and claims it for its own buffer-tab row**, falling back to `header-line-format` only on older Emacs (its `centaur-tabs-display-line`/`centaur-tabs-display-line-format` vars, set via plain `defvar` in `centaur-tabs-elements.el`). Final fix: force centaur-tabs onto `header-line-format` explicitly in `centaur-tabs.el`'s `:init` block (must run before centaur-tabs loads, since `defvar` only takes effect on an unbound variable), freeing `tab-line-format` for a genuine worktree row in `persp.el` (`lg/worktree-tabs-formatted`). Display order top-to-bottom is now tab-bar (persps) → tab-line (worktrees) → header-line (buffers, centaur-tabs) → buffer text — the three-tier layout originally asked for. Entries are numbered to match `lg/worktree-switch-to-N`, highlight the worktree matching the current buffer's `projectile-project-root`, and are clickable (`[tab-line mouse-1]`) to quick-switch. Refreshed via `window-buffer-change-functions`/`window-selection-change-functions` (not just persp-switch hooks), since the highlighted entry depends on the current buffer, which changes far more often than the persp does.

- **Worktree bar shows only open worktrees, not every worktree of the repo** — mirrors how the persp tab bar (`lg/workspaces-formatted`) only lists currently-open perspectives, not every project you could switch to. `lg/worktree--open-list` (`persp-worktree.el`) filters `lg/worktree--list` down to worktrees with at least one live buffer (via `lg/worktree--buffer-for-path`), and is now the shared source for the tab-line bar (`lg/worktree-tabs-formatted`) *and* `lg/worktree-quick-switch`/`switch-left`/`switch-right`/`switch-to-N` — so the numbers in the bar always match what `SPC p 1..9` jumps to. `lg/worktree-switch` (`SPC p w`, open a file) deliberately still uses the full `lg/worktree--list`, since its purpose is to open a worktree you haven't visited yet — that one worktree you can't "switch to" until it has a buffer.
- **Root worktree labeled "root", not the repo name**: `lg/worktree--root-p` detects the main worktree (its `.git` is a directory, vs. a gitdir-pointer file for linked worktrees); `lg/worktree--display-name` uses this to show `"root"` there instead of the repo directory name, which read as just another worktree name and didn't stand out. Used everywhere a worktree gets a short label — `lg/worktree--list` and the tab-line bar.
- **Bar hides itself when only the root worktree is open** — took three attempts. First attempt had `lg/worktree-tabs-formatted` return `""` in that case, which turned out insufficient: `tab-line-format`'s *value* (the `:eval` spec itself) was still non-nil via a single global `setq-default`, so Emacs still reserved an empty tab-line row — the row only fully collapses when the format *variable* itself is nil, not when it evaluates to an empty string. Second attempt dropped the `setq-default` for a buffer-local `tab-line-format` set per window, refreshed via `window-buffer-change-functions`/`window-selection-change-functions` — but this broke the bar *entirely*: those two hooks call their functions with the **frame** as sole argument, not a window (confirmed against Emacs's `window.el`; easy to miss since most window hooks do pass a window). The refresh function expected a window, got a frame, `window-live-p` silently returned nil, and every real firing of the hook was a no-op — only the one-time initialization pass at load actually set anything, and that ran before any worktree buffers existed. Third/current fix: `lg/worktree-tabs-refresh-line-format` now takes an (optional) *frame* and walks `(window-list frame 'no-minibuf)`, refreshing each window's buffer via a separate `lg/worktree-tabs--refresh-window` helper; the load-time initialization pass iterates `(frame-list)` instead of `walk-windows`.
- **Keybindings, split by user convention**: the user distinguishes `[`/`]` (*moving/switching* between things — buffers, workspaces) from `{`/`}` (*rearranging* their order — e.g. the existing `SPC TAB {`/`}` → `+workspace/swap-left`/`-right`). Worktrees turned out to want both: `SPC p [`/`]` switch to the previous/next open worktree (`lg/worktree-switch-left`/`-right`, unchanged); `SPC p {`/`}` now reorder the current worktree's position in the tab strip (`lg/worktree-move-left`/`-right`, new).
- **Worktree tab order is user-rearrangeable and persists per repo**: `lg/worktree--order-table` (`persp-worktree.el`) maps a repo's root-worktree path (a stable key, unlike position-dependent indices) to a custom ordering of worktree paths. `lg/worktree--list` applies this order over the raw `magit-list-worktrees` result when one exists for the repo, appending any new/unknown worktrees at the end in magit's order — so worktrees created or removed since the order was set don't break anything. `lg/worktree-move-left`/`-right` swap the current worktree with its neighbor in this order and persist the result. This order is upstream of `lg/worktree--open-list`, so the bar, `SPC p [`/`]`, and `SPC p 1..9` all reflect it consistently.
- **`SPC p k` closes a worktree's view** (`lg/worktree-kill`), mirroring `+workspace/kill` for a persp: kills every buffer rooted at the current worktree (via a new `lg/worktree--buffers-for-path`, generalizing the existing single-buffer lookup), after first switching to another open worktree's buffer if one exists, or Doom's fallback buffer otherwise — so the current window is never left displaying a buffer about to be killed. Explicitly recomputes `tab-line-format` visibility *after* the kill (not just before), since closing a worktree can be the very thing that drops the open-list back down to "just root," which should hide the bar. Doesn't touch the worktree directory, branch, or anything on disk — closing the view is independent of `hatchery done`/manual worktree removal.
  - `SPC p k`/`SPC p d`/`SPC p x`/`SPC p D` all turned out to already be claimed by Doom's default projectile bindings (`d` = remove known project, `x`/`D` confirmed taken too) — every single free letter under `SPC p` was already spoken for except `k`, which Doom uses for `projectile-kill-buffers` (kill all buffers across every worktree of the project). Resolved by bumping that to `SPC p K` and taking the now-free `SPC p k` for the worktree-scoped kill; with only one worktree open the two commands are equivalent.
  - **Bug: `SPC p k` correctly killed the worktree's visible buffer, but its tab stayed in `lg/worktree--open-list' forever.** Root-caused with a batch-mode Emacs harness (`emacs --batch`, real `projectile`+`magit`, a throwaway git repo with a linked worktree — see the sandbox's headless-Emacs addition below) that exercises the actual functions from this file: a minimal single-buffer/single-window repro came back clean, which ruled out the kill/refresh sequencing logic itself. The user then reproduced it live and found the smoking gun via `(lg/worktree--buffers-for-path path)`: a lingering `#<buffer  *jka-compr-wr-temp*>` — an internal, leading-space-named Emacs buffer (jka-compr's transient compressed-file-write scratch buffer) rooted (via `default-directory`) in the killed worktree. `lg/worktree--buffers-for-path` only excluded minibuffers, not internal buffers, so this invisible buffer alone kept the worktree "open" indefinitely. Fixed by excluding leading-space buffer names, matching the convention `lg/centaur-tabs-buffer-list` (`centaur-tabs.el`) already uses for the same reason.
  - **Bug: `SPC p {`/`}` visibly did nothing (frame "blinked" from the refresh advice, but the bar didn't reorder).** `lg/worktree-move` computed the current worktree's index and swap target against `lg/worktree--list` (*every* worktree of the repo, including ones not open in this persp) rather than `lg/worktree--open-list` (what the bar actually shows). With other, closed worktrees of the repo present, the "neighbor" at `current ± delta` in the full list was often one of those invisible closed worktrees — the order-table genuinely got updated and the refresh advice genuinely fired (hence the blink), but the two open worktrees on screen never swapped with each other. Fixed by computing the swap target within `lg/worktree--open-list`, then locating those two specific worktree paths in the full ordered list to swap there — preserving closed worktrees' relative order while actually moving the one you're looking at. Verified via the same batch harness (`driver4.el`): two open worktrees, `lg/worktree-move-left` now correctly swaps their order.
